# Online Foundation V1 — Phase C

## Status and provisioning boundary

Phase C implements and live-verifies the PostgreSQL identity schema, reviewed Drizzle migration, Hyperdrive Worker database client, durable identity repository, and PostgreSQL-backed `PlayerIdentityResolver`.

Development provisioning is complete. The real development Hyperdrive ID is bound only in the top-level development configuration in `wrangler.jsonc`; test and production binding templates remain inactive until isolated resources exist. Durable `/api/me` behavior is proven both with the supported local direct-connection override and through a temporary Cloudflare remote preview using the actual Hyperdrive resource. This is a development/private-testing checkpoint, not a production deployment.

Phase C adds identity persistence only. It does not add gameplay state, starter inventory, plants, currency, frontend login, production authentication, realtime systems, or deployment.

## Approved infrastructure

- PostgreSQL provider: Neon
- Preferred region: AWS `us-west-2` / Oregon
- Worker connection: Cloudflare Hyperdrive
- Runtime driver: `pg` / node-postgres
- Schema/query layer: Drizzle ORM
- Migration tooling: Drizzle Kit with reviewed SQL committed under `server/db/migrations/`

The combination is supported: the Worker creates one `pg.Client` inside each authenticated request that reaches player resolution, using `env.HYPERDRIVE.connectionString`. Hyperdrive owns the underlying pooled origin connections; no database client or pool is stored in Worker global state.

## Schema

### `players`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Primary key, generated by PostgreSQL |
| `created_at` | timestamptz | Required, defaults to `now()` |
| `updated_at` | timestamptz | Required, defaults to `now()` |

This table intentionally contains no username, display name, Token balance, XP, settings, inventory, or game state.

### `player_external_identities`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Primary key, generated by PostgreSQL |
| `player_id` | UUID | Required FK to `players.id`, cascade on player deletion |
| `provider` | varchar(64) | Required |
| `subject` | text | Required |
| `created_at` | timestamptz | Required, defaults to `now()` |

The unique index on `(provider, subject)` guarantees that one external identity maps to one internal player. The non-unique `player_id` index supports future lookup of multiple linked identities for one player. Provider subjects never become gameplay primary keys.

## Durable identity flow and concurrency

After `DevelopmentIdentityProvider` verifies `account-a` or `account-b`, the PostgreSQL resolver:

1. Looks up `(provider, subject)`.
2. Returns the existing `player_id` when present.
3. Otherwise begins a transaction.
4. Rechecks the mapping inside the transaction.
5. Creates a PostgreSQL-generated player UUID and mapping.
6. Returns the resulting `player_id`.

If concurrent first-login transactions race, the database unique index is authoritative. The losing insert raises PostgreSQL `23505`; that transaction rolls back its newly created player, then the resolver reads and returns the winning mapping. This avoids duplicate mappings and orphan players without advisory locks.

The fixed Phase B Account A/B UUID map is removed from the active implementation. Account subjects remain deterministic, while their internal UUIDs are generated on first durable resolution. No seeds, Tokens, Nursery state, progression, or other starter state is created.

## Request and error behavior

`GET /api/health` remains lightweight and performs no database query.

`GET /api/me` retains its Phase B response contract, but a valid non-production development identity now resolves through PostgreSQL. Missing and invalid credentials are rejected before opening a database connection. Production still selects no development provider and returns 401 before database access.

Unexpected database failures use the generic API 500 response. Server logging records only the request ID and error class name, not SQL, connection strings, database hosts, stack traces, or credential values.

## Drizzle migration workflow

The schema source is `server/db/schema/index.ts`. `drizzle.config.ts` generates and validates migration history without requiring credentials. `drizzle.migrate.config.ts` requires an explicit server-side `DATABASE_URL`.

```powershell
# Generate reviewed SQL after changing the schema.
npm run db:generate

# Validate committed migration snapshots/history.
npm run db:check

# Apply committed migrations to the explicitly selected database.
$env:DATABASE_URL = 'postgresql://...'
npm run db:migrate
Remove-Item Env:DATABASE_URL
```

`drizzle-kit push` is not part of the authoritative workflow. Migrations never run during Worker startup.

`.env.example` documents variable names only. Real URLs must remain in local process environment or a secure secrets system and must never use a `VITE_*` name.

## Neon environment and isolation model

The development Neon project runs PostgreSQL 18 in AWS `us-west-2` / Oregon. It currently uses two separate databases on the development branch:

- `cactigrow`: persistent development data. The reviewed migration is applied here.
- `cactigrow_test`: disposable integration-test data. The gated suite requires an empty identity schema, applies committed migrations, performs its assertions, and removes only the tables and Drizzle history it created.

Automated tests never target `cactigrow`. No production database exists in this model; production must receive an appropriately isolated database or project, credentials, roles, and Hyperdrive configuration before private deployment.

`cactigrow_owner` is the development migration/admin role. `cactigrow_runtime` was created through SQL as a login role with no superuser, database-creation, role-creation, replication, row-security-bypass, or inherited-role membership. It has database `CONNECT`, schema `USAGE`, and `SELECT`/`INSERT` on the two identity tables. It has no schema `CREATE` and no table `UPDATE` or `DELETE`. Normal Worker runtime uses only this role; migration credentials are not used by the Worker.

The opt-in integration test requires:

```powershell
$env:TEST_DATABASE_URL = 'postgresql://.../cactigrow_test?sslmode=require'
$env:CACTIGROW_DATABASE_TESTS = '1'
npm run test:db
Remove-Item Env:TEST_DATABASE_URL
Remove-Item Env:CACTIGROW_DATABASE_TESTS
```

The database name must contain `test`. The test also refuses an existing CactiGrow identity schema, applies migrations from empty state, validates persistence/concurrency/constraints/API behavior, and then removes only its created tables and Drizzle history schema. Never point it at production.

## Hyperdrive provisioning

Cloudflare Hyperdrive configuration `cactigrow-development` connects to the direct Neon development endpoint as `cactigrow_runtime`, requires TLS, and has query caching disabled because identity lookup requires fresh reads and read-after-write consistency. Its real non-secret resource ID is committed only in the development binding. No database URL or password is stored in source. Test and production have no active Hyperdrive bindings.

For local `wrangler dev`, set the supported process-scoped override without committing it:

   ```powershell
   $env:CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE = 'postgresql://...'
   npm run dev:worker
   Remove-Item Env:CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE
   ```

The local override was validated to target database `cactigrow`, role `cactigrow_runtime`, and a direct/unpooled endpoint before both live verification runs.

## Live verification checkpoint

The following checks passed against the provisioned infrastructure:

1. `npm run db:check` validates committed migration history.
2. The committed migration applies from empty state in `cactigrow_test`.
3. The test proves repeated Account A resolution is stable and Account B is distinct.
4. Four concurrent first-login resolutions produce one logical player mapping.
5. PostgreSQL rejects duplicate `(provider, subject)` mappings and orphan identity foreign keys.
6. The suite verifies missing and invalid development identities return 401.
7. Local Worker `/api/health` returns 200 without database access.
8. Live development `/api/me` gives Account A a database-generated UUID, repeats the same UUID, and gives Account B a different UUID.
9. A full Worker process restart preserves both UUIDs.
10. Worker output and API failures expose no credentials, database URL, SQL, or stack trace.
11. A local production-environment run reports production health and rejects the development Account A header with 401 before database access.
12. A temporary Cloudflare remote preview using the actual Hyperdrive resource returns development health, preserves the same Account A/B UUIDs established by local runs, and rejects an invalid identity with 401. The preview was stopped without deploying the Worker.

The `pg` driver currently emits an advisory warning about a future interpretation change for SSL connection-string modes. It did not affect TLS connectivity or any verification result; review explicit certificate-verification settings before production provisioning.

## Recovery baseline

1. Git migration history is the authoritative schema history.
2. Neon history, branch restore, and provider recovery capabilities are the initial database recovery mechanism.
3. Before public alpha, define an independent encrypted logical backup/export schedule, retention, access controls, and restore runbook.
4. Before public alpha, rehearse restoration into an isolated database, apply/verify migration history, compare identity row counts and constraints, and verify Account A/B resolution before declaring recovery ready.

Provider history does not replace independent backups indefinitely.
